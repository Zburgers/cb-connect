# Gate 5 — mobile client and distribution decision freeze (2026-10-14)

**Status:** Product-owner approved architecture and release-direction decision, recorded for review in PR #66. This is **not** approval of the dated Gate 5 execution plan, access to real data, store distribution, credential creation, or production feature exposure.

**Authority:** Sole CB Connect product owner, conversation 2026-10-14. See [Gate 5 plan](../plans/2026-08-01-06-mobile-internal-beta.md), [preflight review](../reviews/2026-10-13-gate-5-mobile-preflight.md), and [D-014 decision register](major-release-decision-register.md).

## Frozen decisions

1. **Single native client:** Build one **Expo + React Native + Expo Router + TypeScript** application in `apps/mobile`, targeting Android and iOS. Do **not** implement parallel SwiftUI and Kotlin/Jetpack Compose applications; do **not** integrate experimental `@expo/ui` SwiftUI or other Swift-specific UI in Gate 5. Native platform bridge code may be added only when necessary for correct Expo/RN operation.
2. **Reuse existing backend:** Clerk native authentication obtains native sessions/Convex tokens; Convex continues to own authoritative cycle state/predictions, role/couple authorization, chat, notification and period/pain mutations. Same user identities and account data in production **when approved**; initially isolated synthetic dev/test systems. No browser-cookie reuse, alternate health business logic or partner-scope authorization in the app.
3. **Android is the committed release deliverable:** Signed, upgradeable, versioned Android APKs via owner-controlled keystore and GitHub Releases. Expose verified public artifact metadata and install instructions from a future `/download` page in the existing Next.js site. Google Play is **not** a Gate 5 prerequisite. Do not publish signing private keys, personal health data or unauthorized prerelease builds.
4. **iOS native parity is an engineering target; personal installation is a gated experiment:** Generate a real-device Expo/RN iOS build using an eligible macOS toolchain/CI. Investigate producing an **unsigned or sideload-signable IPA** and signing/installing via SideStore with the owner's free Apple account. Treat this as an **unverified technical hypothesis** until reproduced on a physical iPhone, tested for login/Convex reconnect and expiry/refresh without health data loss. Do not promise a generally installable IPA or App Store/TestFlight release; Apple provisioning/device limits and signing/refresh rules still apply. No paid Apple Developer membership is planned for Gate 5. A failed iOS signing experiment does **not** block Android.
5. **Website distribution and companion web-app path:** Plan `app/download/page.tsx` for Android APK releases and, **only after verification**, optional iOS personal-install guidance/source manifest. Investigate installable home-screen/PWA behavior as a low-duplication way to use the existing Next.js experience on iPhone. This is distinct from native iOS and needs its own validation; do not promise browser notification equivalence.
6. **Release/version metadata:** Immutable git tags, app semantic release version, Android `versionCode`, iOS build number if applicable, build commit/backend compatibility marker, hashes, changelogs, and recovery guidance. Engineering selects/reviews stable platform IDs and keystore recovery; the owner need not invent bundle identifiers. `tech.builtbynaki.cbconnect` and `.beta` are **provisional**, not registered/final.
7. **Scope:** Native feature parity with approved public-facing web contracts for authentication, onboarding, role/partner dashboard, cycle state, periods and pain logs, corrections/history, couple sharing/revocation, chat, in-app notifications and settings. UI is **not** a direct Next.js DOM/Tailwind/Radix copy: create native presentation and extract safe pure TypeScript types/formatters/validators/design tokens. No push, App Store, Play Store, ML promotion or offline queued health writes in this gate.

## Explicit non-goals and deferred ideas

- **Long-term only — SwiftUI and xtool:** Native SwiftUI prototype or separate iOS client, Linux SwiftPM builds/signing/install via [xtool](https://github.com/xtool-org/xtool), experimental SwiftUI-through-React-Native UI components, and bespoke native component bridges are **out of scope for Gate 5**. Reconsider only on evidence of a concrete native requirement/performance/accessibility limitation or a later product decision. Do not pay for or build an Apple signing service.
- Optional Google Play and Apple App Store/TestFlight/public push distribution belong to the later store/push planning gate and **require separate account and policy authority**. Free personal-device installation is not Apple public distribution.
- No native application implementation until the dated M1–M9 execution plan is approved under the feature-first policy.

## Execution split and acceptance

- **M1–M3:** Expo workspace/contracts, native Clerk + Convex auth, protected shell. Preserve single-writer ownership of manifests/config/shared routing/contracts.
- **M4–M8:** Native rendering of existing backend data and writes, partner/inbox/chat, privacy threat model and adversarial reviews. No duplicate domain estimator or privileged internal Convex APIs in client bundles.
- **M9 Android (required):** Deterministic native build, durable signing identity and backup, installed APK smoke and upgrade checks, secure auth/logout, data privacy, two-user re-pair/revocation and critical UI journey tests, restricted build/telemetry artifacts, GitHub Release + website URL verification.
- **M9 iOS (separately gated):** Build/run on iOS simulator when available; attempt physical-device IPA build + SideStore install using owner's Apple account after explicit on-device authorization; verify release refresh and auth. Record reproducible *pass*, *blocked by tooling*, or *failed* result. Do not substitute an Expo Go session or browser emulation for physical-device proof. Never handle Apple passwords in GitHub, source, logs or chat.
- **Web install path (optional):** Evaluate Next.js manifest, icons and Safari add-to-home-screen; assess Clerk session and privacy in an installed web app.
- **Release blockers remain:** D-011 clinical/health copy where affected, D-012 privacy and production exposure/deletion, D-013 real prediction outcomes, D-018 replacement-partner sharing default, and D-015 beta cohort/staffing. Owner approval of this architecture does not waive them.

**Fallback:** If unpaid iOS native sideloading cannot be demonstrated reliably, ship Android APKs first and offer the existing web experience / qualified installable web app on iPhone. Keep the Expo iOS source maintainable for later work; do not branch into a second SwiftUI client as an immediate workaround.
