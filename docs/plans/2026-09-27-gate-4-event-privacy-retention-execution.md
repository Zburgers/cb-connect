## N1 contract freeze: `G4-EVENT-V1`

Validity can be a state change rather than a fixed date; actual storage retention awaits D-012. Security/account notices require their own separately approved producer and are reserved, not silently emitted.

**Authoritative scheduled-source version (`G4-SOURCE-V1`):** `CycleState.version == 1` and snapshot `contractVersion == 2` describe schemas; neither is a source revision. N2a freezes one internal `notificationScheduleState` row per primary (`by_user_id` on `userId`) with a monotonic integer `sourceRevision`. N2c freezes VEGA's `advanceNotificationSourceAuthority(ctx, primaryId)` helper. Relevant accepted fact create/end/correction/tombstone, eligibility/segment changes, cycle-setting/pause changes and primary timezone changes increment that revision in the same domain mutation, once per committed transition; concurrent writes and equal wall-clock timestamps still get distinct revisions. A failed transaction rolls the increment back; an unchanged/irrelevant write or repeated reconciliation does not advance it. N3a/N3e, N5b/N5d and N8 cover every current writer (`periods.ts`, `users.ts`, `painLog.ts` when it changes timezone, and `cycleContext.ts` when an accepted prediction segment changes the served prediction baseline). Existing period authority/correction/tombstone versions remain the domain authority; this counter is notification scheduling metadata and cannot override them.

`sourceAuthorityVersion` is the canonical versioned tuple of that per-primary revision plus the served cycle/prediction contract and applicable estimator/calibration method versions. No local day, snapshot ID/`generatedAt`, refresh timestamp, raw input hash or provider/template version belongs in that tuple. Snapshot freshness still uses `currentPredictionSnapshotInput`/`predictionSnapshotMatchesCurrent`; an absent/stale/paused/unavailable served V2 prediction suppresses prediction-based work. Once scheduling metadata exists, source transitions keep its revision current even while dispatch is paused; flags-off fresh installs create no source rows or notification events. At first opt-in, initialize scheduling metadata from current authoritative state in the same transaction; no historical backfill. A new serving-method version invalidates old work through the shared reconciliation path; no independent period arithmetic.

Both prediction-window and Late intents store this tuple. Same-day correction or tombstone that still yields `late_or_uncertain`/`AFTER_LATEST_BOUND` cancels the old intent and creates a replacement with the new source key. Incidental snapshot refresh and repeated day-boundary callbacks keep the same source key. `reminderWindowVersion` is a separate monotonic purpose-schedule revision in the user's preference row: relevant enable/disable/local-time changes advance it so a valid replacement cannot collide with a cancelled intent. Repeated identical preference writes do not advance it; unrelated purpose changes do not advance another purpose's version. Cancelled intents never resurrect, delivered/expired work is never replayed, and enabling after the approved validity window does not send a catch-up notification. Both revisions are internal metadata subject to D-012, never evidence/log dimensions.

**Preference-write → reconciliation:** N5c (VEGA, after N5b's helper handoff) makes the purpose/reminder-time mutation in `convex/mutations/notifications.ts` persist its preference revision and call CHRONOS's bounded `reconcileUserSchedule(ctx, userId)` in the **same transaction**. That helper rechecks flags/current served state, cancels/supersedes old pending generations and persists eligible due work plus transactional `runAt` wakeups. Enablement and local-time edits must take effect without a snapshot refresh, domain write, cron or app visit. Disablement cancels current work immediately, while projector/read authorization rechecks prevent a queued callback from exposing revoked work. If recomputation must refresh a snapshot, persist a generation-bound reconciliation continuation before committing; no preference write may depend on an incidental future refresh. Flag-off writes persist preferences without dispatch; re-enablement uses bounded scheduler reconciliation, never an all-user scan. N7b/N8 prove this through the actual preference API and authenticated UI.

**No-write Late transition:** N5a persists a `late_boundary` kind in the existing `notificationDueWork` queue for an opted-in primary's source/window version. Its deadline is the first eligible user-local reminder time on a local day strictly after the shared served `latestDate`; CHRONOS uses calendar/timezone helpers on that bound, without calculating a new period prediction. It uses `by_state_and_due_at` pending pages and a generation-guarded `runAt` wakeup. At wakeup, N3e's `notificationCycleState` adapter re-reads current authority and calls the shared cycle read model; only current `late_or_uncertain` with `AFTER_LATEST_BOUND` creates one Late event. No period mutation, snapshot refresh or dashboard query is required for clock-only entry. Corrections/new start/pause/timezone/preferences supersede the boundary; retained old rows never block the pending prefix. N8 integrates the callback after VEGA and CHRONOS handoff. D-011 keeps this producer/copy off pending approval.

**Projection rule:** Create a domain event with an intended recipient ID inside the committing transaction, but the inbox projector re-reads current user existence, active couple membership, sharing permission where relevant, preference, source authority version, expiry and current snapshot before creating/showing a recipient item. A stored event is never evidence of authorization. For health events the primary is the only V1 recipient; no partner copy can be inferred from `sharingPhase` or `sharingPain`. For relationship events, the sender cannot cause another user's display after link revocation. Recheck on read as well as projection; deny or hide on revocation. Old inbox items must not resurrect after relinking. Cancellation marks work invalid and stops new projection; hiding/redacting old items is non-destructive and may be implemented now.

**Exactly-once logical creation:** One event per catalog key, one inbox item per event/recipient, and one delivery per event/channel/destination identity, enforced by indexed lookup/insert inside transactional mutations. Replays converge; these are application invariants, not Convex unique constraints or a promise of exactly-once network effects. Gate 4 records an atomic in-app projection outcome, never external acceptance or device delivery.

## N1/N2 delivery contract freeze: `G4-DELIVERY-V1`

```text
Domain transaction -> NotificationEvent (why / recipient / authority)
                   -> current policy and channel allowlist
                      -> NotificationDelivery (one destination, durable work)
                         -> in_app adapter -> InboxItem (canonical user surface)
                         -> later external adapter -> DeliveryAttempt -> provider outcome
                      -> reconciliation of due, stuck and unresolved work
```

Inbox and external delivery are sibling channel outcomes of the event. An external delivery never depends on an inbox read or client session. The in-app delivery links its single inbox item; later external deliveries may reference that item for an opaque authorized deep link but do not own its read/dismiss state. No automatic channel fallback, generic event bus, workflow DSL, queue service or new dependency is required.

### Durable records and three keys

`notificationDeliveries` owns `eventId`, `recipientUserId`, channel, opaque destination identity and resolved destination version (if applicable), logical key, `notBefore`, optional `expiresAt`, work state plus separate eligibility and provider-outcome facts, attempt count, `nextAttemptAt`, claim generation/lease and dispatch-start marker, safe cancellation/error code and immutable render identity. Missing time expiry means authority/state validity still applies; it never means permanent authorization. In-app destination identity is the recipient's inbox, requiring no token/destination registry. Add external destination storage only with its adapter and approved lifecycle.

1. **Event key:** the catalog's domain transition/version/recipient components; no snapshot refresh or executor timestamp in it.
2. **Delivery key:** `eventId + channel + stableDestinationId`. In-app uses recipient ID. One installation or verified-address identity per logical destination; token rotation is a version change, not a new delivery key. Changing to a different email/address identity requires an explicit new delivery policy, not an implicit retry.
3. **Provider key:** stable opaque derivation of the delivery key, passed only when the provider supports idempotency with compatible scope/lifetime. The adapter declares support, receipt meanings, safe lookup and retry classifications. Retry count is never part of this key.

`notificationDeliveryAttempts` references a delivery, ordinal/claim generation, start/completion timestamps, resolved destination version and normalized outcome/code/provider ID where available. It cannot supply recipients, copy or eligibility. In-app projection and its successful attempt record commit together; it has no network call. External attempts are created only by a later qualified executor. No runtime fake provider, live webhook or external destination row ships in Gate 4.

### State machine and adapter result

| Current state / fact | Allowed next state and action |
|---|---|
| `pending` or due `retry_wait` | Revalidate eligibility, budget and deadline; fenced claim -> `processing`. In-app may complete claim, projection and `delivered` atomically. |
| `processing`, confirmed acceptance | `accepted`; record provider ID, never equate with delivered/read. In-app -> `delivered` means inbox persistence only, not user display. |
| `accepted`, authenticated confirmed receipt | `delivered` only for that adapter's documented delivery meaning. Provider handoff cannot be relabelled device delivery; read/open remains separate. |
| Known retryable result, definitely not accepted | `retry_wait` with bounded exponential backoff/jitter; provider `Retry-After` is a minimum deadline. Retry only while valid and within the attempt budget. |
| Permanent failure or retry budget exhausted | `failed_permanent` with allowlisted reason; no auto-replay/dead-letter resend. |
| Response lost, timeout after possible dispatch, result-write failure after acceptance | `unknown`; no blind resend. Resolve by provider lookup/receipt or safe same-key retry only with documented provider idempotency. Otherwise remain unresolved for authorized review until validity expires. |
| Source stale/revoked, consent off, invalid destination or deadline passed | `cancelled`, `suppressed` or `expired` as appropriate; no retry. Temporary kill switches pause claiming, retain original expiry, and do not restart a delivery with a new key. |

Eligibility/cancellation and factual provider outcome are separate fields: a late receipt may record that a cancelled send was accepted/delivered, but cannot restore eligibility, resurrect inbox content or trigger retries. Duplicate/out-of-order receipts cannot regress outcome. A conflicting terminal receipt is recorded as a normalized anomaly for reconciliation, not resolved by arrival order alone.

The small adapter result union is `accepted(providerMessageId?) | retryable(errorCode, retryAfter?) | permanentFailure(errorCode) | unknown(errorCode?)`. CB Connect owns purpose/recipient, timing, consent, validity, allowed channels, dedupe and frozen copy. The adapter receives only the current dispatch authorization, resolved destination, stable key and frozen channel payload; it delivers and normalizes outcomes. Channel-specific registration, provider credentials and HTTP details remain adapter-local. Transport/5xx is retryable only when acceptance is excluded or safe provider dedupe exists; a dropped response is ambiguous regardless of its error name.

### Execution, recovery and backpressure

Use native Convex initially. Persist due work/delivery and schedule `runAt` in the same mutation; the durable row is the source of truth, the scheduled function only a wakeup. A wakeup carries row ID and generation and re-reads current state. Corrections supersede the generation and cancel scheduled wakeups where possible; stale/running callbacks still revalidate and become no-ops. [Convex documents atomic mutation scheduling, at-most-once actions without automatic retries, and cancellation limits for already-running actions](https://docs.convex.dev/scheduling/scheduled-functions). Do not rely on action auth propagation or cancellation to prevent a side effect.

A bounded periodic reconciler catches missed/overdue wakeups, due `pending/retry_wait`, expired work, stuck leases, accepted work awaiting expected receipts and invalidated destinations. Use `notificationDueWork.by_state_and_due_at(state,dueAt)` and delivery indexes `by_state_and_next_attempt_at(state,nextAttemptAt)` and `by_state_and_lease_until(state,leaseUntil)`; separate bounded passes per state, cursor continuation and generation fences. Retained terminal/unknown history must not starve due work. Accepted receipt polling uses `by_state_and_next_receipt_check_at(state,nextReceiptCheckAt)`; `unknown` resolution uses `by_state_and_review_at(state,reviewAt)`, never an all-history scan. Actual external poll/webhook ingestion waits for the adapter gate; Gate 4 tests reducers/recovery with injected outcomes.

Claims are transactional compare-and-set with a lease and fencing generation; stale workers cannot write results over a newer claim. A correlated late provider fact is still ingested through the monotonic outcome reducer; fencing stops state overwrite, not factual receipt recording. A recovered claim proven not dispatched can retry. Once a dispatch-start marker is committed, a worker crash may have happened before or after the network call: recovery must classify it `unknown`, not infer failure from timeout. A marker cannot make HTTP and a DB commit atomic. Future batching preserves per-delivery claims/results and only retries the safe subset.

Freeze finite page size, concurrency, maximum attempts, base/capped backoff, lease and receipt deadlines as versioned operational configuration in N2c; RED tests reject absent/unbounded values and use an injected clock/jitter seed. These are work limits, not retention durations. N8 measures and records chosen values against Gate 0 SLO before qualification. For future network executors, enforce shared global/channel/provider budgets in transactional claims, not only per-worker limits; provider throttling/circuit cooldown prevents an outage recovery storm. Gate 4's atomic inbox projector uses bounded pages. Workpool may later replace wakeup execution if measured load warrants it, without replacing delivery rows or ownership; it is not installed by Gate 4.

Metrics are aggregate queue age, retry rate, failures by safe code, queue/processing latency, acceptance and confirmation where supported, expired/suppressed/stuck/unknown counts and duplicate logical keys. No health purpose/type, recipient/destination IDs, payload hashes or small-cohort dimensions in operational telemetry. Detailed purpose/type counters belong only in sanitized synthetic qualification evidence. Control changes keep only protected operator reference, control version and change timestamp under the same minimization/lifecycle rules; no generic audit service or secrets in records.

### Late destination resolution, rendering and receipts

Immediately before dispatch, resolve the current active destination version, then recheck user existence, active membership/generation, relevant sharing, purpose and channel consent, allowed channel, freshness/source version, expiry and all kill switches. Logout/uninstall/token invalidation disables the destination. A rotated token may rebind an unaccepted delivery to the same installation only after current authorization; it cannot retarget an accepted/unknown send and cause a second physical notification. The payload stays identical. Revocation plus external HTTP cannot be atomic: do not claim recall or zero post-revocation external effects once dispatch has begun. In-app authorization and persistence share a mutation and reads recheck authority.

Freeze `templateVersion + locale + variableSchemaVersion + allowlisted immutable variables + payloadHash` on logical-delivery creation, before the first attempt. Gate 4 uses fixed reviewed copy and an opaque route enum; no health/free-text interpolation. The hash covers only this safe canonical payload, not raw source data, and is internal metadata, never telemetry or a de-identification claim. Same delivery key produces the same retry payload; a template edit creates a new version for new deliveries. Existing version implementations remain available while referenced records exist. Source correction cancels/supersedes rather than re-renders an existing delivery. Receipt rechecks do not re-render.

Future receipts require authenticated provider ingress, internal correlation to delivery/attempt/provider ID and idempotent `provider + providerEventId` processing; providers without event IDs need a documented stable normalized key. Store only provider event/message ID, semantic outcome, safe timestamp/code and correlation IDs in restricted storage. Never raw responses. Reducers tolerate duplicates, out-of-order events and late acceptance after cancellation. Receipt storage/credential/token lifecycle and provider-specific retention review are additional adapter acceptance gates; Gate 4 freezes the interface and deterministic tests, not speculative endpoint infrastructure.

**Ship boundary:** Gate 4 qualifies event/policy/delivery lifecycle, in-app persistence, local scheduling, recovery and operations. Fake adapter failure injection proves the reusable core contract; it cannot qualify real push/email/Discord. Each later adapter must demonstrate destination verification/lifecycle, consent, privacy-safe copy, provider capabilities, error/receipt mapping, rate limits, ambiguity handling, outage recovery, retention authority and rollback on its exact code/target. Adding a provider requires a reviewed channel allowlist/version change; installing an adapter never opts a user in.

## Data minimization and retention/deletion contract

Use exact validators and allowlisted reason codes. No `v.any()`, raw template variables, arbitrary errors, webhook responses, message bodies/previews, notes, dates of period/pain, pain scores/tags, diagnosis, phase, hormone/fertility inference, Clerk ID/email/name, auth tokens or external address in new notification storage or evidence. IDs and local due dates are sensitive metadata: keep them server-side; never put them in generic telemetry, public previews or PR artifacts. Render a short reviewed generic inbox label and a link to the authorized source screen, then let that screen enforce its own current authorization. Templates are code/version identifiers plus fixed reviewed copy; no unreviewed interpolation. Generic future external preview is fixed neutral copy only, with external channel adapters disabled. Opaque provider correlation IDs and hashes remain restricted metadata, not anonymous data.
