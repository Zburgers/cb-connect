## N1 contract freeze: `G4-EVENT-V1`

Each event has an immutable type/version, purpose, producer domain reference plus authority version, owner, intended recipient, privacy class, validity rule, stable idempotency key, and allowed channel. **The allowed-channel value for every V1 row is `in_app` only.** `expiry` below means *stop projecting or showing as current*, not permission to delete the record. Validity can be a state change rather than a fixed date; actual storage retention awaits D-012. Security/account notices require their own separately approved producer and are reserved, not silently emitted.

| Type v1 / purpose | Producer → recipient | Class / sensitivity | Validity and stable key components | Supersede/cancel; partner rule |
|---|---|---|---|---|
| `assisted_period_start.v1` / confirm assisted write | accepted confirmed `periodEvents` partner assist → primary | primary-private / health | Until authority version changes or primary no longer has access; `type, periodEventId, authorityVersion, primaryId` | Correct/delete supersedes; never project to partner, including the assisting actor. |
| `assisted_period_end.v1` / confirm assisted end | accepted period end transition → primary | primary-private / health | Same event/version boundary; `type, periodEventId, authorityVersion, primaryId` | Correction/delete supersedes; primary only. |
| `period_window_approaching.v1` / optional care reminder | current served V2 snapshot → primary | primary-private / inferred health | Only designated due local day while snapshot remains current and prediction available; `type, primaryId, latestEligibleStartEventId, sourceAuthorityVersion, dueLocalDay, reminderWindowVersion` (snapshot ID is a separate freshness reference, not the key; `sourceAuthorityVersion` advances only when relevant authoritative inputs change, not on an incidental snapshot refresh) | New start, correction, deletion/tombstone, pause, timezone change, stale snapshot or preference off cancels before projection. No partner projection in V1. |
| `late_status.v1` / optional Late context | approved served Gate 2/3 state → primary | primary-private / inferred health | Only while current Late state remains valid; `type, sourceStateVersion, localDay, primaryId` | State change/pause supersedes. | `pain_check_in.v1` / user-requested reminder | explicit primary request tied to pain log, never score threshold → primary | primary-private / health | Request's selected local day while active; `type, requestId, requestVersion, primaryId` | Edit/cancel/revoke request supersedes. No partner delivery even when `sharingPain` is true; separate privacy approval would be needed. |
| `partner_linked.v1` / link state notice | active link transition → each participating account separately | account/relationship / sensitive | Until link revocation; `type, coupleId, linkGeneration, recipientId` | Revoke cancels partner-visible unread entry. No health data or other partner identity in payload. |
| `partner_message.v1` / chat activity | new `coupleMessages` row → other active member | relationship-private / free text source | While message and active link exist; `type, messageId, recipientId` | Deletion/clear/revoke cancels entry; inbox stores no body or preview. | `connected_since_updated.v1` / relationship setting change | explicit update → other active member | account/relationship / sensitive | Until next setting version/revoke; `type, coupleId, settingVersion, recipientId` | No date/name in inbox payload. |

**Projection rule:** Create a domain event with an intended recipient ID inside the committing transaction, but the inbox projector re-reads current user existence, active couple membership, sharing permission where relevant, preference, source authority version, expiry and current snapshot before creating/showing a recipient item. A stored event is never evidence of authorization. For health events the primary is the only V1 recipient; no partner copy can be inferred from `sharingPhase` or `sharingPain`. For relationship events, the sender cannot cause another user's display after link revocation. Recheck on read as well as projection; deny or hide on revocation. Old inbox items must not resurrect after relinking. Cancellation marks work invalid and stops new projection; hiding/redacting old items is non-destructive and may be implemented now.

**Exactly-once boundary:** One logical outbox row and one inbox item per deterministic key, claimed by an indexed lookup and insert in a Convex mutation with transactional conflict retry. Repeated cron runs/replays must converge. This is *not* a claim that future external providers deliver exactly once. `event_created`, `inbox_projected`, `attempt_claimed`, `provider_accepted`, `failed`, and `device_delivered` are distinct states. Gate 4 never writes an external attempt or claims device delivery.

## Data minimization and retention/deletion contract

Use exact validators and allowlisted reason codes. No `v.any()`, raw template variables, arbitrary errors, webhook responses, message bodies/previews, notes, dates of period/pain, pain scores/tags, diagnosis, phase, hormone/fertility inference, Clerk ID/email/name, auth tokens or external address in new notification storage or evidence. IDs and local due dates are sensitive metadata: keep them server-side; never put them in generic telemetry, public previews or PR artifacts. Render a short reviewed generic inbox label and a link to the authorized source screen, then let that screen enforce its own current authorization. Templates are code/version identifiers plus fixed reviewed copy; no unreviewed interpolation. Generic future external preview is fixed neutral copy only, with channel adapters disabled.

|---|---|---|---|

No duration is proposed here. A validity cutoff, quiet-time window or synthetic fixture cleanup is not a retention period. D-012's existing proposal remains pending; this plan does not mark it approved.

## Flags, cutover and rollback

Proposed server-side flags, all **false by default** and absent treated as false: `CB_CONNECT_NOTIFICATION_OUTBOX_V1` (dark event creation), `CB_CONNECT_NOTIFICATION_PROJECTION_V1` (inbox projection), `CB_CONNECT_NOTIFICATION_INBOX_V1` (recipient reads/UI), and `CB_CONNECT_NOTIFICATION_SCHEDULER_V1` (local due-work creation). Each requires exact target attestation and isolated synthetic qualification before any test enablement. Gate 4 has no push/email/SMS/Discord enable flag. `externalNotificationConsent` is legacy only and never enables new delivery. Keep `CB_CONNECT_PERIOD_PREDICTION_V2` and `CB_CONNECT_PARTNER_PREDICTION_V2` off in production; scheduler emits no prediction event when the served V2 contract is off, paused, unavailable or stale. No legacy arithmetic fallback.

Deploy additive schema and code with flags off; check the protected target and previous artifact before merging because every green `main` CI run deploys Convex/frontend. Cutover must fail-close old Discord callers **before** enabling any Gate 4 inbox path. Rollback disables scheduling, event creation and projection while leaving `CB_CONNECT_NOTIFICATION_INBOX_V1` on so currently authorized existing rows remain readable; if a separate privacy/security response requires disabling reads/UI, rows become inaccessible until that flag is restored and are not deleted. Do not hard-delete as rollback. A Discord shutdown is one-way from this gate: rollback cannot reactivate health delivery. If any old scheduled action can still POST, the cutover fails. Removing `DISCORD_WEBHOOK_URL` from GitHub secrets alone is not proof of Convex revocation (#16); operator verifies name presence only and explicitly removes the stale Convex value after all callers are proven disabled. Do not touch `CLERK_WEBHOOK_SECRET` while repairing the Discord path. A missing configured local reminder time suppresses scheduling; N5 must not silently use 09:00 UTC or invent a quiet-time default.
