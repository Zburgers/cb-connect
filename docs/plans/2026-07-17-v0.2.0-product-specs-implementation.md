### Task 4: Specify Care Loop consent and domain behavior

**Files:**

- Create: `docs/specs/03-consent-sharing-and-care-loop-privacy.md`
- Create: `docs/specs/04-care-loop-v1-domain-and-state-machine.md`
- Reference: `convex/schema.ts`
- Reference: `convex/mutations/couples.ts`
- Reference: `convex/queries/dashboard.ts`
- Reference: `convex/test.fixtures.ts`

**Step 1: Define the effective consent calculation**

Specify the intersection of authenticated relationship, category defaults,
Care Loop permission, immutable share snapshot, recipient, expiry, revocation,
and recipient notification preferences.

**Step 2: Define data separation**

Document private `careCheckIns`, immutable `careShareSnapshots`, bounded
response state on `careRequests`, append-only `careAuditEvents`, and
partner-safe DTOs. Private documents must not cross the partner query boundary.

**Step 3: Define the lean user flow**

Limit v1 to one active expiring card, request-only sharing by default, one to
three helpful and zero to three avoid items, acknowledge/cannot-help partner
responses, and owner cancel/revoke.

**Step 4: Define the state machine**

List every allowed actor transition, stale revision behavior, idempotent retry,
expiry scheduling, cancellation, revocation, and terminal state.

**Step 5: Add validator and index sketches**

Use Convex validators, bounded literal unions plus explicit custom text fields,
fully named indexes, no unbounded arrays, and no client-supplied authorization
IDs.

**Step 6: Add acceptance and pilot criteria**

Include authorization tests, expiry tests, privacy non-inference tests, retry
tests, accessibility cases, card-creation time, acknowledgement rate, cancel
rate, and unwanted-sharing reports.

**Step 7: Commit**

```bash
git add docs/specs/03-consent-sharing-and-care-loop-privacy.md docs/specs/04-care-loop-v1-domain-and-state-machine.md

```

- Create: `docs/specs/05-care-event-outbox-inbox-and-notifications.md`

- Reference: `convex/actions/discord.ts`

**Step 1: Separate notification responsibilities**

Define domain event, inbox item, preference, device registration, delivery plan,
attempt, and receipt records with stable dedupe keys.

**Step 2: Define delivery authorization and privacy**

Require an authorization recheck immediately before sending, generic lock-screen
copy, cancellation on revoke/expiry/unlink, quiet hours, and bounded retries.

**Step 3: Define confidence inputs and outputs**

Specify confirmed-cycle minimums, variability, predicted windows, confidence
labels, data-quality explanations, observed-versus-estimated status, provenance,
and algorithm version.

**Step 4: Define safe degradation**

No prediction is shown when evidence is insufficient. Irregular or missing data
must widen or suppress a window rather than present false precision.

**Step 5: Add tests, rollout, and rollback**

Cover duplicate scheduled work, delivery retries, consent races, DST/quiet-hour
boundaries, insufficient cycle history, corrected dates, and algorithm-version
rollback.
