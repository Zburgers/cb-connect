## Current calendar and write behavior

- Calendar values are `YYYY-MM-DD` strings. Date validation rejects malformed
  dates and future dates against a supplied timezone; absent stored/caller
  timezone resolves to `UTC`.
- Primary start/end/correction mutations accept an optional `timeZone` and
  persist it to `users.timeZone` when supplied and changed. This is current
  behavior, not an approved D-008 policy.
- A new primary or partner-assisted start finds an open period and writes its
  end as the day before the new start. It does not perform a comprehensive
  duplicate/closed-interval overlap check.
- Primary starts write `source: self` and a legacy status field. Partner-
  assisted starts write `source: partner_assist` and are already accepted in
  the primary history; Gate 1 adds explicit certainty/authority metadata and
  primary correction/deletion precedence without introducing a partner
  approval state.
- Primary corrections update the legacy status field. Primary delete currently
  physically removes the row; Gate 1 must replace that path with a
  retention-gated tombstone, not an irreversible delete.
- `autoEndPeriods` remains registered daily. It writes an expected end date
  from cycle settings to open rows and assigns `source: system` only where a
  source was previously absent. This is a confirmed Gate 1 problem, not a
  migration decision.
- Timeline rendering treats an open event's configured period length as an
  effective end and then calls the cycle calculation. Therefore estimated and
  recorded state are not yet cleanly separated.
