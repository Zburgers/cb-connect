## Gate 3 TypeScript to Python golden-parity bridge

The TypeScript runner is the current executable reference. Its dataset format is `g3-cycle-benchmark-data-v1`, manifest protocol `G3-BENCH-V1`, metric version `cycle-benchmark-metrics-v5`, and paired bootstrap version `user-cluster-percentile-95-2000-v1`. The future Python bridge must consume a **synthetic-only**, versioned export from that runner. It must not create a second eligibility or benchmark authority or add Python to `package.json`, the Next.js route, Convex mutation, or user request path.

1. Preserve the checked-in golden manifest shape and CLI guard: `loadCycleBenchmarkFiles` accepts only `fixtures/cycle-benchmark` as a synthetic CLI dataset. Export canonical, sorted fold records and the TypeScript report through a separate synthetic bridge envelope; do not add fields to the G3 manifest. Bind that envelope to fixture ID, protocol/data/metric/bootstrap/estimator/calibration versions, code commit, split salt **ID** (never secret salt), file checksums, event authority/cutoff version, and `containsRealUserData: false`. Keep raw synthetic date histories only in fixture inputs, not generic evidence logs.
2. Match each fold by synthetic user key, partition, segment, prediction cutoff, target index, prior eligible anchors/intervals, inclusion/reason codes, estimator ID, point date, residual, interval bounds, quality and subgroup labels. Assert exact calendar-day arithmetic, half-up rounding, median/tie behavior, `possible_missing_log_v1`, and chronology before comparing aggregate metrics.
3. Match the frozen 60/20/20 user-level split; all folds for a user stay in one partition. Development selects an estimator, calibration fits residual bands, and locked evaluation never selects or refits it. Match the exact Gate 3 baselines `configured_v1` and `all_median_v1` (`last3_median_v1` is a candidate), history/variability bands, abstention, signed-error direction, paired differences, coverage, and promotion verdict. Comparison with the shipped estimator is an additional Gate 7 research rule, not a change to frozen G3-BENCH-V1.
4. Mirror the executable paired-bootstrap rule: seed SHA-256 over `manifestSha256:partition:metricVersion:estimatorId:baselineId`, take its first eight hex digits as an unsigned 32-bit state, update with `state = (1664525 × state + 1013904223) mod 2^32`, resample sorted user clusters with replacement for 2,000 draws, aggregate fold-weighted sums/counts, and use ceiling nearest-rank 2.5%/97.5% quantiles. CI is null with fewer than two scored users. Specify numeric serialization/tolerance for non-integer summaries before parity without changing Gate 3 thresholds.
5. The checked-in seven-user golden run has **zero calibration fit outcomes**, so it cannot demonstrate interval or quality calibration parity. Add separate in-process synthetic test fixtures (still using the frozen TypeScript functions and a bridge envelope) with at least 20 calibration residuals, at least five prior personal residuals, at least two evaluation users and a non-null bootstrap CI; also cover null-CI and insufficient-calibration branches. These fixtures are not alternate CLI real datasets or promotion evidence.
6. Fail closed on unknown versions, missing/extra fold, changed checksum, future correction, cross-user partition overlap, target-derived calibration, changed subgroup assignment, or a Python-only field influencing a Gate 3 metric. Compare JSON after canonical key ordering, with exact discrete fields and preregistered numeric precision. Synthetic parity proves bridge implementation only; it cannot authorize real evaluation or model promotion.

The current runner requires D-013 authority and an existing shared durable ledger outside checkouts before real locked evaluation. A Python process must not bypass that ledger or open the same holdout independently. Any later real bridge needs one approved outcome-opening owner and a single receipt/manifest identity across languages and machines.

## Synthetic simulation and leakage fixtures — design only

| Fixture | Simulated input / mechanism | Required assertion |
| --- | --- | --- |
| Stable, variable, outlier and shift | Separate generated users with known interval parameters; one isolated long interval; a sustained shift after a known cutoff. | Recover direction of variation; an outlier widens uncertainty before forcing a center shift; no future shift affects an earlier fold. No performance claim. |
| Possible missing log | The frozen 28/29/58/28 history plus a generative skipped-tracking mechanism with known synthetic truth. | Preserve the 58-day observed interval and flag suspicion only under the frozen heuristic; never invent an intervening period or treat absent logging as biological lateness. |
| Sparse and certainty/provenance | One start, 2–3 intervals, approximate/`legacy_unknown` events, accepted current partner-assisted exact start, and legacy unreviewed assistance. | Match Gate 3 anchor eligibility and personalization floor; current authorized assistance is eligible immediately, while unknown/approximate facts remain excluded. |
| Time and correction | Leap day, timezone boundary, a correction/tombstone after cutoff, and a new private segment. | Earlier fold and immutable snapshot inputs stay unchanged; later folds use current authority; no interval crosses segments. |
| Partition and calibration trap | Same synthetic user duplicated under different rows; a deliberately outcome-informed feature or calibration residual; a subgroup label computed using future observations. | User-level partition and cutoff checks reject all leaks; deliberately leaking run differs from clean run, while the production path rejects it. |
| Withdrawal and shadow isolation | Synthetic withdrawal at a chosen cutoff; a newer shadow candidate than a visible snapshot; sharing and notification toggles. | Withdrawn material is excluded under the future approved lifecycle; candidate never appears in primary, partner, notification, API or exported read models, and cannot suppress the existing served prediction. |

Simulation recovery needs preregistered parameter ranges and explicit failure cases: non-convergence, poor prior/posterior predictive fit, missing-label ambiguity, insufficient subgroup size, and abstention. A known synthetic mechanism is a test oracle, not evidence that the mechanism describes CB Connect users. Any public reproduction must report transfer limits and must not be joined to CB Connect outcomes without separate authority.

## Reproducibility and isolation contract for a later plan

- **Lineage:** immutable run ID binds source Git SHA, protocol hash, fixture/dataset manifest and content hashes, approved extraction/query/schema version, consent snapshot and cutoff (for future authorized data), split salt ID, environment lock hash, config, seeds, estimator/calibration/metric/bootstrap versions, reviewer record, and artifact checksums. Never put split secrets, direct IDs, free text, pain values or unrestricted date histories in a general registry, PR, CI log or report.
- **Artifacts and access:** isolate offline Python dependencies and any approved extracts/posterior draws from application dependencies and public Git/CI artifacts. Governance must name encryption, access roles, audit logs, retention, withdrawal/deletion and incident process before a real extract exists. Sensitive extracts and posterior draws require approved restricted storage **outside Git**; a `docs/evidence/` path does not provide per-path access control. Only redacted pointers, counts/hashes and review receipts may enter Git evidence.
- **Evaluation:** freeze manifest, candidate, subgroups, metric code and holdout binding before outcome review. Preserve chronological folds and user-level split; compare against both approved Gate 3 baselines (`configured_v1`, `all_median_v1`) **and** the shipped estimator. Gate 7's extra 0.25-day paired MAE, 77–83% coverage and subgroup limits remain hard research criteria, with convergence and simulation checks. Null/negative results stay recorded. D-013's one-opening ledger remains authoritative for real Gate 3 outcomes.
- **Shadow:** use an isolated, access-controlled candidate store or prove indexed/query-level separation before import. Do not assume the existing `displayStatus: "shadow"` field is enough: the present latest-snapshot read can be displaced by a shadow row. Future tests must prove zero output in primary/partner/notification/API paths, no raw feature/history import, no `periodEvents` writes, no automatic retraining or promotion, correction-aware delayed scoring, and disable on consent, lineage, leakage or drift failure. Both production Gate 3 prediction flags **must remain off**; no research switch may turn them on.
- **Claims:** research outputs are not evidence of fertility, contraception safety, diagnosis or observed ovulation. No such claim or user-visible experimental prediction is authorized.
- **Rollback:** disable future shadow generation/import and retain the currently shipped statistical/configured behavior. Research artifact withdrawal/deletion follows an approved D-012/D-016 policy; this document specifies no destructive operation or retention duration. Any user-visible ML requires a separate PRD, authority and rollout plan.
